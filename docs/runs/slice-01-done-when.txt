    | # Ledger: connection pool exhaustion
    | 
    | Alert: `LedgerPoolIdleLow` fires when idle database connections in any ledger pod stay below 20 for 3 minutes.
    | 
    | ## How the pool is sized
    | 
    | Each ledger pod keeps a pool of at most 40 connections to postgres-primary. There are 6 ledger pods, so ledger can
    | hold up to 240 connections. postgres-primary has `max_connections = 300`, and the remaining 60 are reserved for
    | migrations, replication and humans.
    | 
    | A connection is returned to the pool when its transaction ends. Long transactions are the usual reason the pool
    | drains: a single report query holding a connection for minutes takes it out of rotation for everyone.
    | 
    | ## Diagnosis
    | 
    | ### Check the pool
    | 
    | ```bash
    | kubectl -n ledger exec deploy/ledger -- ledgerctl pool stats
    | # idle=8 in_use=32 waiting=17 max=40
    | ```
    | 
    | `waiting` above 0 means requests are queueing for a connection. Queueing over 2 seconds shows up as payments
    | latency, because payments writes a ledger entry on every charge.
    | 
    | ### Find long transactions
    | 
    | ```sql
    | SELECT pid, now() - xact_start AS age, state, left(query, 80) AS query
    | FROM pg_stat_activity
    | WHERE usename = 'ledger' AND xact_start IS NOT NULL
    | ORDER BY age DESC
    | LIMIT 10;
    | ```
    | 
    | Anything older than 30 seconds is suspect. The nightly reconciliation job runs at 02:00 UTC and is the most common
    | offender when it overlaps with peak traffic in APAC.
    | 
    | ## First steps
    | 
    | 1. Run `ledgerctl pool stats` on two or three pods to confirm the pool is low everywhere, not on one pod.
    | 2. Find long transactions with the query above. Cancel a reconciliation query with `SELECT pg_cancel_backend(pid)`;
    |    it is safe to cancel and resumes from its last checkpoint.
    | 3. Do not raise the pool size above 40. Six pods at 50 would need 300 connections, which is all of postgres-primary.
    | 4. If the pool stays low with no long transactions, check postgres-primary itself for lock waits or replication
    |    problems.
    | 
    | ## Escalation
    | 
    | Page the database on-call if pool exhaustion lasts over 15 minutes with no long transaction to cancel.

Q: Ledger writes started failing with 'cannot execute INSERT in a read-only transaction' right after postgres-primary had a failover. Why, and what exactly should I do?
verdict: ANSWERED   (qwen3.5:9b-q4_K_M, ask/1, 3263 prompt + 199 output tokens, 24570 ms)

Ledger writes fail because ledger pods hold pooled connections to the old primary for up to 10 minutes, which
is no longer the leader after a failover [C1]. These stale connections can still read but every write fails as
read-only since the old primary was demoted [C3]. To fix this, first confirm the failover has finished and a
new primary is accepting writes [C1]. Then recycle the ledger connection pools so every pod reconnects to the
new primary right away using: `kubectl -n ledger exec deploy/ledger -- ledgerctl pool recycle --all-pods`
[C1]. Watch the write error rate; it should drop to zero within one minute of the recycle [C1]. Do not restart
ledger pods instead of recycling, as a rolling restart takes about 6 minutes and drops in-flight requests
[C1]. If errors continue after a recycle, the new primary may itself be read-only, so page the database on-
call [C1].

    | # Postgres primary: failover and switchover
    | 
    | postgres-primary is a 3-node Patroni cluster. Patroni promotes a replica automatically when the leader stops
    | renewing its lock for 30 seconds (`ttl = 30`). A switchover is the planned version of the same thing.
    | 
    | ## Check the cluster state
    | 
    | ```bash
    | kubectl -n postgres exec postgres-primary-0 -- patronictl list
    | ```
    | 
    | The `Leader` row is the current primary. A node in `running` state with role `Replica` is a healthy standby.
    | After a failover, confirm that the new leader accepts writes:
    | 
    | ```sql
    | SELECT pg_is_in_recovery();  -- false on the primary
    | ```
    | 
    | ## What clients see during a failover
    | 
    | - Writes fail for 30–45 seconds while Patroni detects the failure and promotes a replica.
    | - The `postgres-primary-rw` service follows the leader, but existing connections stay attached to the old node.
    |   After the old leader is demoted, those connections can still read but every write fails as read-only.
    | - Clients with connection pools must reconnect. Services that cache connections for a long time (ledger keeps them
    |   up to 10 minutes) keep failing writes until they recycle their pools.
    | 
    | ## Planned switchover
    | 
    | ```bash
    | kubectl -n postgres exec postgres-primary-0 -- patronictl switchover --candidate postgres-primary-1 --force
    | ```
    | 
    | Announce a switchover in #db-changes 15 minutes ahead, and run it outside 12:00–14:00 UTC, the payments peak.
    | 
    | ## After any failover
    | 
    | 1. Confirm the new leader with `patronictl list` and `pg_is_in_recovery()`.
    | 2. Tell the ledger on-call or run the ledger pool recycle yourself; ledger is the main client with long-lived
    |    connections.
    | 3. Check replication lag on the remaining replicas; the old leader rejoins as a replica once it is healthy.
    | 4. Open a postmortem if the failover was not planned.
